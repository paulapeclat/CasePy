01 / estrutura de dados

@dataclass

Uma forma elegante de criar classes que só guardam dados, sem escrever código repetitivo.

Imagine uma ficha de cadastro de jogador numa LAN house. Ela tem campos fixos: nome, CPF, telefone. Você não precisa inventar os campos toda vez — a ficha já define o que deve ser preenchido. @dataclass faz exatamente isso: define a estrutura dos seus dados em Python.

01
O problema sem @dataclass
▾
Para representar um evento de kill, você precisaria escrever tudo na mão — muito código para guardar 4 campos:
sem_dataclass.py
class KillEvent:
    def __init__(self, player_id, kills, damage, timestamp):
        self.player_id = player_id
        self.kills     = kills
        self.damage    = damage
        self.timestamp = timestamp

    def __repr__(self):  # pra aparecer legível no print
        return f"KillEvent({self.player_id}, kills={self.kills})"

# 9 linhas para guardar 4 campos — todo esse trabalho manual
02
A solução com @dataclass
▾
Python gera o __init__, o __repr__ e a comparação automaticamente:
com_dataclass.py
from dataclasses import dataclass

@dataclass
class KillEvent:
    player_id: str
    kills:     int
    damage:    int
    timestamp: float

# Usando:
ev = KillEvent(player_id="PLR-001", kills=3, damage=1800, timestamp=1700000000.0)
print(ev)
# KillEvent(player_id='PLR-001', kills=3, damage=1800, timestamp=1700000000.0)
O : str, : int depois do nome do campo é a type hint. Documenta o tipo esperado. Python não bloqueia em runtime, mas o VS Code avisa se você passar o tipo errado.
03
Valor padrão nos campos
▾
Campos opcionais recebem valor padrão com =:
valor_padrao.py
@dataclass
class KillEvent:
    player_id: str
    kills:     int
    damage:    int
    timestamp: float
    validated: bool = False  # opcional, padrão False

ev = KillEvent("PLR-001", 3, 1800, 1700000000.0)
print(ev.validated)  # False
04
frozen=True — imutável como um recibo
▾
Eventos já registrados não deveriam ser alterados. frozen=True proíbe qualquer modificação:
frozen.py
@dataclass(frozen=True)
class KillEvent:
    player_id: str
    kills:     int

ev = KillEvent("PLR-001", 3)
ev.kills = 99  # FrozenInstanceError — não pode mudar!
Use frozen=True para eventos do passado (auditoria). Use sem frozen para objetos que ainda estão sendo construídos durante a partida.
05
__post_init__ — validar na criação
▾
Método especial que roda automaticamente depois do __init__. Ideal para validar os campos:
post_init.py
@dataclass
class KillEvent:
    player_id: str
    kills:     int
    damage:    int

    def __post_init__(self):
        if not self.player_id:
            raise ValueError("player_id não pode ser vazio")
        if self.damage < 0:
            raise ValueError(f"damage inválido: {self.damage}")
        if self.kills < 0:
            raise ValueError(f"kills não pode ser negativo: {self.kills}")

# Evento inválido é rejeitado na criação:
ev = KillEvent("PLR-001", kills=-1, damage=500)
# ValueError: kills não pode ser negativo: -1
02 / valores fixos

Enum

Evita erros de digitação em strings e deixa o código mais legível e seguro.

Imagine um formulário com a pergunta "Resultado: ( ) Positivo ( ) Negativo". Você só pode marcar uma das duas — não existe "Positivo" escrito diferente. Enum define o conjunto fixo de valores possíveis para um campo.

01
O problema sem Enum
▾
Tipos de evento como strings soltas causam bugs silenciosos:
sem_enum.py
ev1 = {"type": "kill"}   # funciona
ev2 = {"type": "klil"}   # typo — ninguém avisa
ev3 = {"type": "Kill"}   # maiúscula — falha silenciosa no if
ev4 = {"type": "KILL"}   # qual é o certo afinal?
Erros de string só aparecem em runtime — muitas vezes horas depois, num log difícil de rastrear.
02
A solução com Enum
▾
event_type.py
from enum import Enum

class EventType(Enum):
    KILL        = "kill"
    DAMAGE      = "damage"
    SESSION_END = "session_end"
    ASSIST      = "assist"

# Usando — sem aspas, sem typo:
ev_type = EventType.KILL
print(ev_type)           # EventType.KILL
print(ev_type.value)     # "kill"
print(ev_type == EventType.KILL)  # True
03
Usando Enum com @dataclass e match/case
▾
game_event.py
@dataclass
class GameEvent:
    player_id:  str
    event_type: EventType  # só aceita valores do Enum
    value:      int

# Criando eventos com segurança:
ev = GameEvent("PLR-001", EventType.KILL, 3)

# Despachando por tipo (Python 3.10+):
match ev.event_type:
    case EventType.KILL:
        processar_kill(ev)
    case EventType.DAMAGE:
        processar_dano(ev)
    case EventType.SESSION_END:
        fechar_sessao(ev)
match/case com Enum é o padrão moderno. Se chegar um tipo novo que não existe, o código levanta erro imediatamente — melhor que falhar silenciosamente.
03 / cálculo lazy

@property

Transforma um método em algo que parece um atributo simples. Recalcula sempre que você acessa.

Seu celular mostra "bateria restante em horas". Isso não é um campo fixo — é calculado na hora a partir da bateria atual dividida pelo consumo médio. Mas pra você aparece como se fosse um número simples. @property faz o mesmo: parece atributo, executa cálculo por baixo.

01
O problema: campo salvo vs calculado
▾
Se você salvar o KDA como campo, ele fica desatualizado quando kills mudam:
problema.py
class Player:
    def __init__(self, kills, deaths, assists):
        self.kills   = kills
        self.deaths  = deaths
        self.assists = assists
        self.kda     = (kills + assists) / max(deaths, 1)
        # Problema: player.kills += 1 não atualiza self.kda!

p = Player(5, 2, 1)
p.kills += 3
print(p.kda)  # ainda mostra o valor antigo: 3.0 :(
O KDA calculado uma vez no __init__ nunca se atualiza automaticamente. Fica "stale" (obsoleto).
02
A solução com @property
▾
player_stats.py
@dataclass
class Player:
    kills:   int
    deaths:  int
    assists: int
    wins:    int
    games:   int

    @property
    def kda(self) -> float:
        return (self.kills + self.assists) / max(self.deaths, 1)

    @property
    def win_rate(self) -> float:
        return self.wins / max(self.games, 1)

# Usando — parece campo, é cálculo:
p = Player(kills=8, deaths=2, assists=3, wins=6, games=10)
print(p.kda)       # 5.5  — sem parênteses!
print(p.win_rate)  # 0.6
p.kills += 2
print(p.kda)       # 6.5  — atualizado automaticamente!
Note que você chama p.kda sem parênteses, como se fosse um atributo. O @property intercepta a leitura e executa o método por baixo.
03
As três fórmulas do pipeline
▾
KDA
(K + A) / max(D,1)
Kills + Assists / Deaths. max(D,1) evita divisão por zero.
Win rate
wins / total_games
Proporção de vitórias. ×100 para percentual.
Dano médio
sum(dmg) / games
Total de dano por partidas jogadas. Indica agressividade.
04 / memoização

Cache

Como evitar sobrecarregar o banco de dados repetindo os mesmos cálculos caros.

Imagine que você pergunta pro Google "capital do Brasil" e ele vai no banco de dados toda vez. Absurdo — a resposta nunca muda. O Google memoriza respostas frequentes. Cache é isso: guardar o resultado de algo caro para não refazer quando a pergunta é a mesma.

requisição de métrica
→
cache hit?
→
sim → retorna direto
|
não → calcula no banco
→
salva no cache
→
retorna resultado
01
@lru_cache — o mais simples
▾
Para funções puras (mesmo input = mesmo output), use @lru_cache:
lru_cache.py
from functools import lru_cache

@lru_cache(maxsize=256)
def calcular_rank_historico(player_id: str) -> str:
    # Simula consulta pesada ao banco
    historico = buscar_banco(player_id)  # caro!
    return processar_rank(historico)

# 1ª chamada: vai ao banco (lento)
rank = calcular_rank_historico("PLR-001")

# 2ª chamada com mesmo id: retorna do cache (instantâneo!)
rank = calcular_rank_historico("PLR-001")

print(calcular_rank_historico.cache_info())
# CacheInfo(hits=1, misses=1, maxsize=256, currsize=1)
maxsize=256 = guarda no máximo 256 resultados. Quando enche, descarta o menos recentemente usado (LRU). Passe maxsize=None para guardar tudo — use com cautela.
02
Cache com TTL — para dados que mudam
▾
KDA muda a cada partida. Precisamos de cache que expira após um tempo:
ttl_cache.py
import time

_cache: dict = {}
TTL = 300  # 5 minutos em segundos

def get_kda(player_id: str) -> float:
    agora = time.time()

    # Está no cache e ainda não expirou?
    if player_id in _cache:
        valor, salvo_em = _cache[player_id]
        if agora - salvo_em < TTL:
            print("cache hit!")
            return valor  # retorna sem ir ao banco

    # Cache vazio ou expirado: recalcula
    kda = calcular_kda_no_banco(player_id)
    _cache[player_id] = (kda, agora)  # guarda com timestamp
    return kda
A lógica é sempre: 1) existe no cache? 2) ainda é válido? Se sim, retorna. Se não, calcula, salva e retorna.
03
Quando invalidar o cache
▾
invalidar.py
def registrar_kill(player_id: str, kills: int):
    salvar_no_banco(player_id, kills)

    # KDA mudou — cache está desatualizado, remove
    if player_id in _cache:
        del _cache[player_id]

# Para @lru_cache, use .cache_clear():
calcular_rank_historico.cache_clear()  # limpa tudo
05 / cross-cutting concerns

Decoradores

Adicionar comportamento (log, timing, retry) sem modificar a função original.

Todo caixa de banco precisa verificar identidade antes e registrar a transação depois. Você não modifica cada caixa individualmente — cria um procedimento padrão que envolve qualquer caixa automaticamente. Decorador é esse procedimento padrão aplicado a funções.

01
Como um decorador funciona por dentro
▾
@decorator é açúcar sintático. Por baixo, é só uma função recebendo outra:
como_funciona.py
# Escrever isso:
@audit_log
def processar_kill(event):
    ...

# É exatamente igual a:
def processar_kill(event):
    ...
processar_kill = audit_log(processar_kill)
# audit_log recebe a função e retorna uma versão "embalada"
02
Construindo o @audit_log do zero
▾
audit_log.py
import time
from functools import wraps

def audit_log(func):            # 1) recebe a função
    @wraps(func)                # 2) preserva nome e docstring
    def wrapper(*args, **kwargs):  # 3) aceita qualquer assinatura
        t0 = time.perf_counter()
        print(f"[AUDIT] Iniciando {func.__name__}")
        try:
            resultado = func(*args, **kwargs)  # chama a original
            elapsed = time.perf_counter() - t0
            print(f"[AUDIT] OK em {elapsed:.3f}s")
            return resultado
        except Exception as e:
            print(f"[AUDIT] ERRO: {e}")
            raise             # propaga o erro
        finally:
            print(f"[AUDIT] Fim de {func.__name__}")
    return wrapper              # 4) retorna a versão embalada

# Usando:
@audit_log
def processar_kill(event):
    # lógica de negócio limpa, sem log aqui
    return event.kills * 100
*args captura argumentos posicionais, **kwargs captura os nomeados. Isso faz o wrapper funcionar com qualquer função independente da assinatura.
03
Por que @wraps é obrigatório
▾
sem @wraps
print(processar_kill.__name__)
# "wrapper"  ← errado!
print(processar_kill.__doc__)
# None ← docstring sumiu!
com @wraps(func)
print(processar_kill.__name__)
# "processar_kill" ← correto
print(processar_kill.__doc__)
# docstring preservada
Sem @wraps, logs de auditoria mostrariam "wrapper" como nome de todas as funções — inútil para rastrear problemas.
06 / análise estatística

NumPy stats

Matemática rápida em listas de números. Faz em uma linha o que levaria um loop inteiro.

Você tem uma planilha com o dano de 10.000 jogadores. Para calcular a média, poderia somar célula por célula (loop Python) ou pressionar "=MÉDIA(A1:A10000)" e ter a resposta instantânea. NumPy é esse "=MÉDIA" — opera em todos os valores de uma vez, rodando em C por baixo.

01
Por que não usar listas Python normais?
▾
lista Python — lento
damages = [1200, 1840, 900, 2200]
total = 0
for d in damages:
    total += d
media = total / len(damages)
# lento com 1 milhão de valores
NumPy — ~100x mais rápido
import numpy as np
damages = np.array([1200, 1840, 900, 2200])
media = np.mean(damages)
# opera em C — veloz com 1M valores
02
As funções principais no pipeline
▾
numpy_stats.py
kdas    = np.array([1.2, 3.5, 0.8, 5.1, 2.9, 4.4])
damages = np.array([900, 1840, 600, 2200, 1500, 1900])

np.mean(kdas)           # 2.98  — média aritmética
np.median(kdas)         # 3.2   — valor do meio (robusto a outliers)
np.std(kdas)            # 1.49  — desvio padrão (consistência)
np.min(kdas)            # 0.8   — pior partida
np.max(kdas)            # 5.1   — melhor partida
np.percentile(kdas, 90) # 4.85  — top 10% começa aqui
mean é sensível a outliers (um smurf deturpa a média). median é mais robusto — use para representar o desempenho típico.
03
Filtros sem loop — boolean indexing
▾
Filtrar um array com uma condição retorna só os elementos que satisfazem:
boolean_index.py
kdas = np.array([1.2, 3.5, 0.8, 5.1, 2.9])

# Máscara: array de True/False
mascara = kdas > 3
print(mascara)        # [False  True False  True False]
print(kdas[mascara])  # [3.5  5.1] — só os True

# Contar quantos acima da média:
media = np.mean(kdas)
acima = np.sum(kdas > media)  # True conta como 1
print(f"{acima} jogadores acima da média")
A "máscara" é um array de True/False. Ao usá-la como índice (kdas[mascara]), o NumPy retorna só os elementos onde é True — sem nenhum loop.
04
np.where e np.argsort — classificar e rankear
▾
rank_classify.py
kdas = np.array([1.2, 3.5, 0.8, 5.1, 2.9])

# np.where: se/senão vetorizado
tiers = np.where(kdas >= 3.0, "Gold", "Silver")
print(tiers)
# ['Silver' 'Gold' 'Silver' 'Gold' 'Silver']

# np.argsort: índices que ordenariam o array
ordem = np.argsort(kdas)[::-1]  # [::-1] = decrescente
print("ranking:", kdas[ordem])
# [5.1  3.5  2.9  1.2  0.8] — do melhor ao pior
